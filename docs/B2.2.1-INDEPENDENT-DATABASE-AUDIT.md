## 1. Role, Perspective & Audit Methodology

This audit is conducted from the objective standpoint of a **Senior Independent Database Architect, Data Model Reviewer, and Product Requirements Auditor**. Acting strictly as a third-party evaluator, this review does not defend, rationalize, or automatically validate the prior design produced in B2.2. 

A syntactically valid Prisma schema (`prisma validate -> valid`) is **not** equivalent to an accurate, complete, or correct business domain model. The primary inquiry of this evaluation is:

> **How closely does the proposed B2.2 relational data model match the actual product requirements documented in the official Gapji Digital Marketing Platform specification (`marketing-platform-phase1-frontend-pages-1.pdf`)?**

To provide actionable, transparent governance, two distinct scores are computed:
1. **Product Requirements Compliance Score:** Measures how faithfully the entities, attributes, cardinalities, and workflows satisfy the 29-page official product specification.
2. **Database Architecture Quality Score:** Measures technical rigor, relational integrity, multi-tenant boundary safety, data type precision, indexing efficiency, and migration feasibility.

## 7. Multi-Tenancy & Security Architecture Review

### 7.1 Critical Finding: The Composite Foreign Key Fallacy
In [`docs/B2.2-DOMAIN-DATA-MODEL-REPORT.md`](file:///F:/marketing-platform-backend/docs/B2.2-DOMAIN-DATA-MODEL-REPORT.md) §6.2, the design claims:
> *"Prisma Composite Relations: This guarantees that PostgreSQL foreign keys can bind on (campaignId, organizationId) directly, making cross-tenant relational linkage structurally impossible at the database engine level."*

**Independent Verification:**
Inspecting [`docs/B2.2-PROPOSED-SCHEMA.prisma`](file:///F:/marketing-platform-backend/docs/B2.2-PROPOSED-SCHEMA.prisma) reveals that **not a single composite foreign key relationship was actually implemented in the schema**.
While parent models (`Campaign`, `Lead`, `Task`) contain composite uniqueness decorators:
```prisma
model Campaign {
  ...
  @@unique([id, organizationId])
}
```
All referencing child models continue to use standard single-column foreign keys:
```prisma
model Lead {
  campaignId String? @db.Uuid
  campaign   Campaign? @relation(fields: [campaignId], references: [id], onDelete: SetNull)
}

model Cost {
  campaignId String? @db.Uuid
  campaign   Campaign? @relation(fields: [campaignId], references: [id], onDelete: SetNull)
}
```
**Architecture Impact:**
Because the child models do not reference `[campaignId, organizationId]`, PostgreSQL foreign key constraints will **NOT** prevent cross-tenant referencing! A rogue query or service defect can insert a `Lead` belonging to Organization A with a `campaignId` belonging to Organization B, and PostgreSQL will accept it without constraint violation.
*Verdict:* True database-level cross-tenant protection is currently **UNIMPLEMENTED**; isolation currently depends 100% on application-level NestJS service validation.

### 7.2 Multi-Tenancy Strengths
- Every single business model includes direct `organizationId UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE`.
- Tenant indexes (`@@index([organizationId])`) are consistently placed across all 36 scoped models.
- Global identity (`User`) is cleanly isolated from tenant membership (`OrganizationMembership`).

## 9. Financial and Currency Modeling Review

### 9.1 Precision & Serialization Invariants
- **Database Storage:** Preserves `Decimal(12, 2)` across `Campaign.budget`, `Campaign.spend`, `Cost.amount`, `Lead.salesValue`, `SmsCampaign.costAmount`, and `Equipment.purchaseCost`. Complies with `PROJECT-DECISIONS.md §2`.

- **Organization-Scoped Currency:** Modeled via `Organization.currency Currency @default(TOMAN)`.
- **No Automatic 10x Conversion:** The data model strictly avoids hardcoded exchange multipliers, preserving raw numerical integrity.

### 9.2 Financial Aggregation Architecture
The relationship `Campaign ||--o{ Cost` correctly enables dynamic spend auditing (`spend = SUM(Cost.amount)`). The schema allows nullable `campaignId` on `Cost`, which supports logging general agency overhead costs not tied to a specific marketing campaign (PDF p. 11 §9).

## 10. Configurable Settings vs PostgreSQL Enums Review

### 10.1 The Lead Status Architectural Conflict
- **Documented Specification (PDF Page 23 §28):** Under Organization Settings, the document explicitly defines tabs for customizable lists:
  `انواع کمپین، منابع لید، وضعیت‌های لید، دلایل ردشدن، دسته‌بندی هزینه`
  And explicitly states:
  `وضعیت‌های لید: ستون «گروه» (باز/برنده/بازنده)` (Lead Statuses: Column "Group" [Open / Won / Lost]).
- **B2.2 Decision:** Defined `LeadStatus` as a static PostgreSQL Enum:
  `enum LeadStatus { new, contacted, qualified, proposal, customer, lost }`.
- **Audit Assessment:** This is a major structural contradiction. By using a PostgreSQL Enum, organizations cannot add custom sales stages (e.g., "مذاکره قرارداد", "منتظر پرداخت") or group them into Open/Won/Lost as required by the Organization Settings page.
- **Recommendation:** Retain `LeadStatus` enum for default MVP pipeline stability, but add `leadStatusKey String` on `Lead` referencing `OrganizationTaxonomy` for Phase 2 extensibility.

## 14. Prioritized Audit Findings

### 14.1 Critical Findings (Must be corrected before schema implementation)
1. **[CRIT-01] Composite Foreign Keys Unimplemented Despite Documentation Claims:**
   - *Source:* B2.2 Report §6.2 vs B2.2 Proposed Schema.
   - *Defect:* While `@@unique([id, organizationId])` was added to parent models, child models (`Lead`, `Cost`, `Task`) still reference single-column `id`. PostgreSQL will NOT block cross-tenant foreign key linkages at the database level.
   - *Correction:* Update Prisma relations to reference composite keys: `fields: [campaignId, organizationId], references: [id, organizationId]`.
2. **[CRIT-02] Target Audience Cardinality Error (N:1 instead of M:N):**
   - *Source:* PDF Page 9 (§6 Step 2) & Page 14 (§11).
   - *Defect:* `TargetAudience` has `campaignId String?`, restricting an audience to a single campaign and preventing reuse across campaigns.
   - *Correction:* Remove `campaignId` from `TargetAudience` and create an associative join table `CampaignAudience` with `@@unique([campaignId, targetAudienceId])`.
3. **[CRIT-03] Equipment Domain Mismatch (Asset Management vs Event Gear Checklist):**
   - *Source:* PDF Pages 10 (§7), 17 (§18), 19 (§21).
   - *Defect:* Modeled as fixed IT asset inventory (`purchaseDate`, `purchaseCost`) with no link to Campaign or Webinar. Product requires event-specific gear checklists, shortages tracking, procurement due dates, and equipment templates (`قالب‌های تجهیزات`).
   - *Correction:* Redesign Equipment to include `EquipmentTemplate` and `EventEquipment` junction model linking equipment to Campaigns and Webinars with readiness status (`available`, `incomplete`, `not_procured`).

### 14.2 Major Findings (Important functional gaps)
4. **[MAJ-01] Missing Recipient-Level SMS Tracking Table (`SmsRecipient`):**
   - *Source:* PDF Page 17 (§17).
   - *Defect:* `SmsCampaign` only tracks aggregate counters. Lacks table for individual numbers, delivery status, and incoming reply text required to support "Create lead from repliers".
   - *Correction:* Add `SmsRecipient` model with `(id, smsCampaignId, mobile, status, replyText, leadId)`.
5. **[MAJ-02] Conflict Between Static LeadStatus Enum and Dynamic Settings Taxonomy:**
   - *Source:* PDF Page 23 (§28).
   - *Defect:* Product allows organizations to customize Lead Statuses with a Group column (`باز / برنده / بازنده`). B2.2 hardcoded `LeadStatus` as a PostgreSQL enum.
   - *Correction:* Maintain enum for Phase 1 MVP, but document migration to `OrganizationTaxonomy` for Phase 2.
6. **[MAJ-03] Missing Notification Preference Matrix Model:**
   - *Source:* PDF Page 7 (§3).
   - *Defect:* Omitted model for `Event Type × Channel (in-app, email)` notification switches.
   - *Correction:* Add `NotificationPreference` model with `(organizationId, userId, eventType, inAppEnabled, emailEnabled)`.
7. **[MAJ-04] Incomplete KPI Metric & Alert Rule Attributes:**
   - *Source:* PDF Page 13 (§11).
   - *Defect:* `KpiMetric` lacks `formula` and `direction` (higher/lower is better); `KpiAlertRule` lacks `message` and `suggestedAction`.
   - *Correction:* Add missing attributes to `KpiMetric` and `KpiAlertRule`.
8. **[MAJ-05] Missing Task Link and Outcome Field on Creative Ideas:**
   - *Source:* PDF Page 22 (§25).
   - *Defect:* `Idea` model lacks `taskId` and `outcomeNotes` fields required by the UI.
   - *Correction:* Add `taskId String? @db.Uuid` and `outcomeNotes String? @db.Text` to `Idea`.

### 14.3 Minor Findings (Improvements and refinements)
9. **[MIN-01] Missing Data Fetch Method on Platform:**
   - *Source:* PDF Page 11 (§8). Add `retrievalMethod String` (`manual / API / Import`) to `Platform`.
10. **[MIN-02] Missing Saved Mapping and Duplicate Policy on ImportJob:**
    - *Source:* PDF Pages 12–13 (§10). Add `fieldMapping String? @db.Text` and `duplicatePolicy String?` to `ImportJob`.
11. **[MIN-03] Missing WordPress Rejected Requests Log:**
    - *Source:* PDF Page 24 (§29). Add `WordpressRejectedLog` model for webhook troubleshooting.
12. **[MIN-04] Migration Backfill Requirement for Campaign `organizationId`:**
    - *Source:* Production Schema. Adding `organizationId NOT NULL` requires a documented two-stage migration.
