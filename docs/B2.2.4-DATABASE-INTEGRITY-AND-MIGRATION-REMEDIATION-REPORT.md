## 1. Executive Summary

Phase **B2.2.4** remediates the critical data integrity risks, unintended cascading deletion paths, and relational integrity gaps identified in the B2.2.3 audit report. 

While Phase B2.2.2 successfully expanded the domain model to 46 models and introduced compound foreign keys for multi-tenant isolation, it inadvertently introduced high-risk cascading deletions on core financial transactions and customer CRM records. In addition, exactly one relation between organization-scoped models (`Cost.importJob`) remained as an unprotected single-column foreign key.

### Summary of Completed Remediations:
1. **CRIT-A — Financial & Customer Data Protection:**  
   Changed referential action on `Cost.campaign` and `Lead.campaign` from `onDelete: Cascade` to `onDelete: Restrict`. In the PostgreSQL database, any attempt to delete a `Campaign` that has associated financial cost entries or customer lead records is strictly rejected by the database engine, preventing catastrophic accidental data loss.
2. **CRIT-B — Idea Preservation on Task Deletion:**  
   Changed `Idea.task` referential action from `onDelete: Cascade` to `onDelete: Restrict`. Deleting an operational execution task in the task workspace will no longer cascade to erase the originating brainstorming idea in the ideation room.
3. **MAJ-A — 100% Compound Foreign Key Coverage:**  
   Added `@@unique([id, organizationId])` to `model ImportJob` and updated `Cost.importJob` to a full compound foreign key referencing `[importJobId, organizationId]`. All 42 relations between organization-scoped models in the schema now enforce true PostgreSQL engine-level multi-tenant isolation.
4. **MAJ-B — Migration & Baseline Safety Protocol:**  
   Regenerated the baseline migration DDL (`migration.sql`) to incorporate the new `RESTRICT` constraints and compound foreign key for `ImportJob`. Formally analyzed the migration's baseline-from-empty nature and documented the required deployment procedure for existing versus greenfield databases.
5. **Quality Verification & Tests:**  
   Verified via Prisma validation (`prisma validate` -> valid with 0 errors, 0 warnings), Prisma Client regeneration (`prisma generate`), TypeScript compilation (`tsc --noEmit`), NestJS build (`nest build`), and 10/10 automated unit and static integrity tests (`pnpm test`).

## 5. CRIT-A Correction & Evidence: Protect Lead and Cost Records

### 5.1 Problem Statement
In B2.2.2, `Cost.campaign` and `Lead.campaign` were configured with `onDelete: Cascade`. This meant that executing `DELETE FROM campaigns WHERE id = :id` in PostgreSQL would trigger a cascading delete across all `costs` (financial expenses) and `leads` (customer prospect records) associated with that campaign. In financial accounting and CRM systems, customer records and monetary expenditure logs must be permanent and immutable.

### 5.2 Implementation Decision & Rationale
- **Category:** `IMPLEMENTATION DECISION` & `TECHNICAL RECOMMENDATION` (Enforcing `PROJECT-DECISIONS.md` §2 and Product Document p. 11 §9, p. 14 §14).
- **Why `SetNull` is Incompatible with Compound Keys:**  
  In a multi-tenant compound foreign key `(campaignId, organizationId) REFERENCES campaigns(id, organizationId)`, the `organizationId` column is `NOT NULL`. If `onDelete: SetNull` were specified, PostgreSQL would attempt to set both `campaignId` and `organizationId` to `NULL`, triggering a `NOT NULL` constraint violation on `organizationId`. Prisma CLI correctly issues a validation error/warning against `SetNull` on required compound fields.
- **Why `onDelete: Restrict` is the Correct Choice:**  
  Setting `onDelete: Restrict` instructs the PostgreSQL database engine to reject any delete operation on `campaigns` if active rows in `costs` or `leads` reference that campaign. If a user wishes to delete a campaign, they must either explicitly reassign the leads and costs, or archive the campaign instead.

### 5.3 Code Evidence

#### `apps/api/prisma/schema.prisma` (Cost model, lines 668–670):
```prisma
model Cost {
  ...
  organization   Organization  @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  campaign       Campaign?     @relation(fields: [campaignId, organizationId], references: [id, organizationId], onDelete: Restrict)
  ...
```

#### `apps/api/prisma/schema.prisma` (Lead model, lines 738–740):
```prisma
model Lead {
  ...
  organization      Organization      @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  campaign          Campaign?         @relation(fields: [campaignId, organizationId], references: [id, organizationId], onDelete: Restrict)
  ...
```

#### `migration.sql` (Generated PostgreSQL DDL):

## 6. CRIT-B Correction & Evidence: Preserve Idea When Its Task Is Deleted

### 6.1 Problem Statement
In B2.2.2, `Idea.task` had `onDelete: Cascade`. In the marketing room workflow (Product Document p. 21–22 §25), approved ideas can be converted into tasks ("ایجاد تسک از ایده"). If the resulting task is subsequently cancelled or deleted in the tasks workspace, deleting the task must NOT cause the creative idea to disappear from the idea backlog.

### 6.2 Implementation Decision & Rationale
- **Category:** `DOCUMENTED REQUIREMENT` (p. 21 §25) & `IMPLEMENTATION DECISION`.
- **Referential Action Choice:**  
  Because `Idea` enforces multi-tenant compound isolation via `fields: [taskId, organizationId], references: [id, organizationId]`, and `organizationId` is required (`NOT NULL`), Prisma disallows `onDelete: SetNull`.  
  Therefore, `onDelete: Restrict` was implemented. In PostgreSQL, if a task is linked to an idea as its execution vehicle, deleting the task is blocked until the idea's task link is disassociated or the task is archived. This guarantees that creative ideas and their `outcomeNotes` are permanently protected against accidental deletion.

### 6.3 Code Evidence

#### `apps/api/prisma/schema.prisma` (lines 1286–1289):
```prisma
model Idea {
  ...
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  campaign       Campaign?    @relation(fields: [campaignId, organizationId], references: [id, organizationId], onDelete: Cascade)
  task           Task?        @relation("IdeaCreatedTask", fields: [taskId, organizationId], references: [id, organizationId], onDelete: Restrict)
  ...
```

#### `migration.sql` (Generated PostgreSQL DDL):
```sql
ALTER TABLE "ideas" ADD CONSTRAINT "ideas_taskId_organizationId_fkey" 
FOREIGN KEY ("taskId", "organizationId") REFERENCES "tasks"("id", "organizationId") 
ON DELETE RESTRICT ON UPDATE CASCADE;
```

## 7. MAJ-A Correction & Evidence: Complete Cost.importJob Composite Foreign Key

### 7.1 Problem Statement
The B2.2.3 audit identified that among all 42 relations between organization-scoped models, exactly one relation was omitted from compound foreign key isolation: `Cost.importJob` referenced `import_jobs(id)` via single-column foreign key. Consequently, PostgreSQL could not block a cost record in Tenant A from referencing an import job belonging to Tenant B.

### 7.2 Implementation Decision & Rationale
- **Category:** `IMPLEMENTATION DECISION` & `TECHNICAL RECOMMENDATION`.
- **Targeted Fix:**  
  1. Added `@@unique([id, organizationId])` to `model ImportJob`.
  2. Updated `Cost.importJob` relation to reference `fields: [importJobId, organizationId], references: [id, organizationId]`.
  3. Applied `onDelete: Restrict` to ensure an audit `ImportJob` cannot be deleted while financial `Cost` records are linked to it.
  4. Added `@@index([importJobId])` on `Cost` to optimize lookup performance.

### 7.3 Code Evidence

#### `apps/api/prisma/schema.prisma` (ImportJob model, lines 1397–1400):
```prisma
model ImportJob {
  ...
  @@unique([id, organizationId]) // Compound Foreign Key Target (MAJ-A)
  @@index([organizationId])
  @@index([organizationId, status])
  @@map("import_jobs")
}
```

#### `apps/api/prisma/schema.prisma` (Cost model, lines 673–681):
```prisma
model Cost {

  importJob      ImportJob?    @relation(fields: [importJobId, organizationId], references: [id, organizationId], onDelete: Restrict)

  @@index([organizationId])
  @@index([organizationId, date])
  @@index([campaignId])
  @@index([platformId])
  @@index([categoryId])
  @@index([importJobId])
  @@map("costs")
}
```

#### `migration.sql` (Generated PostgreSQL DDL):

ALTER TABLE "costs" ADD CONSTRAINT "costs_importJobId_organizationId_fkey" 
FOREIGN KEY ("importJobId", "organizationId") REFERENCES "import_jobs"("id", "organizationId") 
ON DELETE RESTRICT ON UPDATE CASCADE;

## 8. MAJ-B Migration & Baseline Safety Analysis

### 8.1 Nature of the Prepared Migration
The migration script located at `apps/api/prisma/migrations/20261108103000_foundation_database_schema/migration.sql` is a **fresh-database baseline DDL script generated with `--from-empty`**.

- **Total SQL Size:** 67,118 bytes.
- **Statements:** 24 `CREATE TYPE`, 46 `CREATE TABLE`, 118 `CREATE INDEX`, 110 `ALTER TABLE ... ADD CONSTRAINT`, 1 `INSERT INTO organizations`, 1 `UPDATE campaigns`.
- **Transactionality:** PostgreSQL DDL statements are transactional. If any statement fails during execution inside a standard transaction block, the entire migration rolls back cleanly without leaving partial tables.

### 8.2 Safe Adoption Protocol for Existing vs. Greenfield Databases

| Database Target State | Deployment Safety Assessment | Required Safe Procedure |
| :--- | :--- | :--- |
| **Fresh Database (Staging / Production Greenfield)** | **100% Safe.** Executes all 46 tables, enums, constraints, and inserts the default seed organization. | Run standard `prisma migrate deploy`. |
| **Existing Database with Populated Tables** | **CANNOT be run directly.** Running this script against an existing database containing tables will fail immediately (`relation "campaigns" already exists`). | **DO NOT run `prisma migrate deploy`.** Follow the documented Prisma Baseline procedure below. |

### 8.3 Recommended Prisma Baseline Procedure for Existing Databases
When provisioning against an existing database where pre-B2.2 tables exist:
1. Back up the PostgreSQL database (`pg_dump`).
2. Mark the foundation migration as applied without running it:
   ```bash
   pnpm exec prisma migrate resolve --applied 20261108103000_foundation_database_schema
   ```
3. If structural schema diffs exist, generate an incremental migration:
   ```bash
   pnpm exec prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script > incremental.sql
   ```
4. Review and execute the incremental script.

## 13. Remaining Security Requirements for Phase B2.3

As established in Section 11 of the assignment, the following security controls were intentionally kept out of scope for B2.2.4 and must be addressed in Phase B2.3:
1. **Eliminate Client-Supplied `organizationId`:** Remove `organizationId` from `CreateCampaignDto` and `UpdateCampaignDto` to prevent IDOR vulnerabilities.
2. **Implement Server-Side Tenant Context:** Extract active `organizationId` strictly from authenticated JWT/session tokens using NestJS execution context.
3. **Tenant-Scoped Repository Queries:** Ensure `findAll()` and other repository queries strictly include `where: { organizationId: activeTenantId }`.
4. **Deprecate Default Fallback:** Remove `DEFAULT_ORGANIZATION_ID` fallback from application services once authentication is active.
